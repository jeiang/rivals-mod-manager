# Tauri packaging, signing, updater hosting, and CI survey

Research for issue #17. Fact sheets only; the decision is issue #18.

Scope: a Tauri v2 desktop app (ADR 0001) shipping to Windows, macOS, and Linux. Dimensions: what the bundler produces per OS and which bundles the updater can update; what the updater needs served and how GitHub Releases can host it; code signing and notarization per OS, including what unsigned builds look like to users; GitHub Actions builds for all three targets and how they fit the existing tag-triggered `.github/workflows/release.yml`; and what nixpkgs offers for `cargo-tauri`, the Linux webview stack, and Node. All claims cite primary sources (Tauri docs and repos, GitHub docs and runner-images, Apple and Microsoft docs, SignPath terms, nixpkgs source), accessed 2026-09-02.

Versions at access time: tauri-action `action-v1.0.0` (2026-06-29), updater plugin `updater-v2.11.0` (2026-08-31), `softprops/action-gh-release` v3.0.3 (2026-08-30), nixpkgs-unstable rev `e8be7818` (2026-08-29).

## Bundles per OS

- **Target list.** `bundle.targets` "currently supports `["deb", "rpm", "appimage", "nsis", "msi", "app", "dmg"]` or `"all"`" (default `"all"`); the CLI equivalent is `tauri build --bundles` ([config reference](https://v2.tauri.app/reference/config/), [distribute overview](https://v2.tauri.app/distribute/)). `bundle.createUpdaterArtifacts` (default `false`) additionally produces the updater artifacts and `.sig` files; the value `"v1Compatible"` produces the legacy zipped v1 artifacts instead ([config reference](https://v2.tauri.app/reference/config/)).
- **Windows.** Either `.msi` via WiX Toolset v3 or `-setup.exe` via NSIS. MSI "can only be created on Windows as WiX can only run on Windows systems" and needs the VBSCRIPT optional feature; NSIS can be cross-compiled from Linux/macOS with LLVM/LLD and `cargo-xwin`, described as less tested ([Windows installer](https://v2.tauri.app/distribute/windows-installer/)). Architectures: x64 default, i686 via `i686-pc-windows-msvc`, ARM64 via `aarch64-pc-windows-msvc` (needs the VS "C++ ARM64 build tools"; the NSIS installer itself stays x86 and runs under emulation). WebView2 install modes (`bundle.windows.webviewInstallMode`, default `downloadBootstrapper`, silent): `downloadBootstrapper` ~0 MB/needs internet, `embedBootstrapper` ~1.8 MB, `offlineInstaller` ~127 MB, `fixedRuntime` ~180 MB, `skip`. NSIS `installMode`: `currentUser` (default, no admin, `%LOCALAPPDATA%`), `perMachine`, `both` ([Windows installer](https://v2.tauri.app/distribute/windows-installer/), [config reference](https://v2.tauri.app/reference/config/)). The bundler downloads its own WiX and NSIS toolsets into `~/.tauri` or the OS cache dir on first use ([nsis/mod.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/windows/nsis/mod.rs), [msi/mod.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/windows/msi/mod.rs)).
- **macOS.** `.app` bundle and `.dmg`; both require running `tauri build` "in a Mac computer" ([app bundle](https://v2.tauri.app/distribute/macos-application-bundle/), [DMG](https://v2.tauri.app/distribute/dmg/)). Default `bundle.macOS.minimumSystemVersion` is `"10.13"` ([config reference](https://v2.tauri.app/reference/config/)). `--target universal-apple-darwin` "requires both `aarch64-apple-darwin` and `x86_64-apple-darwin` targets to be installed" ([CLI reference](https://v2.tauri.app/reference/cli/)). DMG caveat: "icon sizes and positions are not applied when creating DMGs on CI/CD platforms" ([DMG](https://v2.tauri.app/distribute/dmg/)).
- **Linux.** `.deb`, `.rpm`, `.AppImage` (plus AUR/Snap/Flatpak guides). The `.deb` depends on `libwebkit2gtk-4.1-0` and `libgtk-3-0` (plus `libappindicator3-1` with a tray) ([Debian](https://v2.tauri.app/distribute/debian/)). All three guides say to build on the oldest base system you intend to support, naming Ubuntu 22.04 / Debian 12 as the baseline because newer glibc raises the app's minimum (`GLIBC_2.33 not found` style failures) ([AppImage](https://v2.tauri.app/distribute/appimage/), [RPM](https://v2.tauri.app/distribute/rpm/)). AppImage is built with linuxdeploy, grows the artifact "from the 2-6 MB range to 70+ MB", cannot be cross-compiled for ARM ("linuxdeploy ... currently does not support cross-compiling ARM AppImages"), and `bundleMediaFramework` adds ~15-35 MB of GStreamer ([AppImage](https://v2.tauri.app/distribute/appimage/), [config reference](https://v2.tauri.app/reference/config/)). deb/rpm document ARM cross-compilation via `armv7-unknown-linux-gnueabihf` / `aarch64-unknown-linux-gnu` ([Debian](https://v2.tauri.app/distribute/debian/), [RPM](https://v2.tauri.app/distribute/rpm/)).
- **Host summary.** MSI: Windows only. `.app`/`.dmg`: macOS only. AppImage/deb/rpm: Linux (ARM AppImage: native ARM only). NSIS: Windows, or cross-compiled from Linux/macOS. No official one-page cross-compilation matrix exists; these are the per-guide statements above.

## Updater plugin

- **Updatable formats.** Windows: `.msi` and NSIS `-setup.exe` (each with a `.sig`); macOS: `.app.tar.gz` + `.sig`; Linux: `.AppImage` + `.sig` only, so deb/rpm installs are not self-updatable ([updater plugin](https://v2.tauri.app/plugin/updater/)). Desktop only (no Android/iOS); requires Rust 1.77.2+ ([plugin README](https://github.com/tauri-apps/plugins-workspace/tree/v2/plugins/updater)).
- **What must be served.** Either a static JSON manifest or a dynamic endpoint. Static: `version` (SemVer), optional `notes` and `pub_date` (RFC 3339), and `platforms.<os>-<arch>` entries each with `url` and `signature`; keys are `linux|windows|darwin` × `x86_64|aarch64|i686|armv7`. Dynamic: `204 No Content` = no update, `200` with `{version, url, signature, notes?, pub_date?}` = update. Endpoint URLs may use `{{current_version}}`, `{{target}}`, `{{arch}}`. Config: `plugins.updater.endpoints` (HTTPS enforced unless `dangerousInsecureTransportProtocol`), `plugins.updater.pubkey` (key content, not a path), `plugins.updater.windows.installMode` = `passive|basicUi|quiet` ([updater plugin](https://v2.tauri.app/plugin/updater/)).
- **Install behavior.** "On Windows the application is automatically exited when the install step is executed due to a limitation of Windows installers" ([updater plugin](https://v2.tauri.app/plugin/updater/)).
- **Keys.** `tauri signer generate -w ~/.tauri/myapp.key` produces the key pair; at build time `TAURI_SIGNING_PRIVATE_KEY` (path or content) and optional `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` must be set, and the bundler emits the `.sig` files when `createUpdaterArtifacts` is on. The docs warn: "if you lose this key you will NOT be able to publish new updates to the users that have the app already installed" ([updater plugin](https://v2.tauri.app/plugin/updater/)). There is no documented rotation mechanism; the pubkey is compiled into the app config. The CLI signs with the `minisign` crate and the plugin verifies with `minisign-verify` ([tauri-cli Cargo.toml](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-cli/Cargo.toml), [updater Cargo.toml](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/Cargo.toml)). This signature is independent of OS code signing (Authenticode / Developer ID).
- **GitHub Releases hosting.** The docs' example endpoint is `https://github.com/user/repo/releases/latest/download/latest.json` ([updater plugin](https://v2.tauri.app/plugin/updater/)). tauri-action generates and uploads that file when `uploadUpdaterJson` is true (default): "Whether to upload a static JSON file for the updater using GitHub Releases as the CDN"; `updaterJsonPreferNsis` (default `false`) picks NSIS over MSI when both exist; `uploadUpdaterSignatures` (default `true`) uploads the `.sig` files ([action.yml](https://github.com/tauri-apps/tauri-action/blob/dev/action.yml)). The README notes that with a caller-created release and `releaseId` but no `tagName`, `latest.json` URLs point at `releases/latest/download/<bundle>` ([tauri-action README](https://github.com/tauri-apps/tauri-action)). The name `latest.json` is convention from these examples, not a stated requirement of the plugin.
- **Not in the docs.** The updater page does not say whether macOS updates require a Developer ID signature; the plugin's own signature check is what is documented as mandatory ([updater plugin](https://v2.tauri.app/plugin/updater/)).

## Signing and notarization

### macOS

- **Requirements.** Developer ID Application certificates and notarization are only in the paid Apple Developer Program, USD 99/year; the free Apple account has neither ([compare memberships](https://developer.apple.com/support/compare-memberships/)). Tauri's guide says the free tier is for development/testing and cannot notarize, and that "Notarization is required when using a *Developer ID Application* certificate" ([macOS signing](https://v2.tauri.app/distribute/sign/macos/)).
- **Notarization rules.** Since macOS 10.15 "all software built after June 1, 2019, and distributed with Developer ID must be notarized." The notary service requires Developer ID signatures (not ad hoc or development certs), Hardened Runtime, and a secure timestamp; since November 1, 2023 it accepts uploads only from `notarytool` / Xcode 14+ ([Apple notarization doc](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)).
- **Tauri tooling.** Signing: `APPLE_CERTIFICATE` (base64 `.p12`, exported via `openssl base64 -A -in certificate.p12`), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY` or `bundle.macOS.signingIdentity`. Notarization runs automatically during `tauri build` when either `APPLE_ID` + `APPLE_PASSWORD` (app-specific) + `APPLE_TEAM_ID` or `APPLE_API_ISSUER` + `APPLE_API_KEY` + `APPLE_API_KEY_PATH` are set; `--skip-stapling` exists. `bundle.macOS.hardenedRuntime` defaults to `true`; `bundle.macOS.entitlements` takes a plist path ([macOS signing](https://v2.tauri.app/distribute/sign/macos/), [config reference](https://v2.tauri.app/reference/config/)).
- **Unsigned / ad-hoc UX.** macOS Sequoia removed the Control-click override; users must go to System Settings > Privacy & Security to allow unsigned or unnotarized software (Apple developer news, 2024-08-06: [Sequoia Gatekeeper change](https://developer.apple.com/news/?id=saqachfa)). Apple's user-facing steps are Privacy & Security > "Open Anyway", after which the app is remembered as an exception ([Apple support 102445](https://support.apple.com/en-us/102445)). Tauri supports ad-hoc signing via `signingIdentity: "-"` for Apple Silicon, which "does not prevent macOS from requiring users to whitelist installation in Privacy & Security settings" ([macOS signing](https://v2.tauri.app/distribute/sign/macos/)). No Apple primary source was found for the `xattr -d com.apple.quarantine` workaround; it is not cited here.

### Windows

- **Tauri config.** `bundle.windows.certificateThumbprint`, `digestAlgorithm`, `timestampUrl`, `tsp`, and `signCommand`, "used to use any codesign tool that can sign Windows executables". The guide covers OV/EV certificates, Azure Key Vault (via `relic`), Azure Artifact Signing (formerly Trusted Signing, via `artifact-signing-cli` with `AZURE_CLIENT_ID` / `AZURE_CLIENT_SECRET` / `AZURE_TENANT_ID` in a `signCommand`), and a GitHub Actions example importing a base64 `.pfx` from `WINDOWS_CERTIFICATE` / `WINDOWS_CERTIFICATE_PASSWORD` secrets. It states signing is not required to run the app if users accept the SmartScreen warning ([Windows signing](https://v2.tauri.app/distribute/sign/windows/), [config reference](https://v2.tauri.app/reference/config/)).
- **SmartScreen.** Reputation is built from two signals, publisher certificate and file hash. Unsigned: "Windows protected your PC", user must choose "Run anyway"; self-signed: "Same behavior as no signature"; valid OV/EV: still warned as unrecognized until reputation accumulates, but the publisher name is shown. "EV certificates no longer bypass SmartScreen." Unsigned files start from zero reputation with every release; reputation carries across versions only when signed with the same publisher identity. "There is no exact threshold, but it can take several weeks and hundreds of clean installs." There is no consumer submission mechanism for reputation. Windows 11 Smart App Control "will block execution of unsigned files unless the file has a positive reputation" ([SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)).
- **Azure Artifact Signing (formerly Trusted Signing).** Microsoft's recommended non-Store option, "Starts at $9.99/month" ([SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)); Basic includes 5,000 signatures/month and 1 of each certificate profile type, Premium 100,000 and 10 (the [pricing page](https://azure.microsoft.com/en-us/pricing/details/trusted-signing/) renders prices client-side, so the USD figures beyond "starts at $9.99" were not confirmed from a static page). Public Trust identity validation: organizations in the US, Canada, EU, UK, Australia, NZ, Japan, South Korea, Singapore, Switzerland, Norway, Israel; "Individual developers must be located in the United States or Canada"; individual validation is driven from the Azure billing account and a Verified ID flow (government ID via AU10TIX); processing 1 to 20 business days ([quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart)). Requires a paid Azure subscription (no free/trial/sponsored), keys live in FIPS 140-3 Level 3 HSMs, certificates are never handed out, no EV certificates are or will be issued, certificate lifetime is short (the FAQ cites three days for the anti-malware profile), and the CA is "Microsoft ID Verified Code Signing PCA 2021" ([FAQ](https://learn.microsoft.com/en-us/azure/artifact-signing/faq), [overview](https://learn.microsoft.com/en-us/azure/artifact-signing/overview)). The GitHub Action is `azure/trusted-signing-action` ([repo](https://github.com/azure/trusted-signing-action)). The quickstart lists 15 supported Azure regions (US, Brazil, EU, Japan, Korea, Poland, Switzerland).
- **SignPath Foundation (free for OSS).** "For OSS projects, our services are free of charge"; keys are held in SignPath's HSM and the certificate is issued to the project via the Foundation ([signpath.org](https://signpath.org/)). Terms: OSI-approved license without commercial dual-licensing, no proprietary components, actively maintained and already released, only the maintaining team may sign, binaries must be built verifiably from the project's own source in CI, MFA for all members, defined committer/reviewer/approver roles with code review, "Every release needs manual approval for signing", product metadata set on binaries, no security-scanning/hacking features, and a published "Code signing policy" crediting SignPath.io and SignPath Foundation plus a privacy statement ([SignPath terms](https://signpath.org/terms)). GitHub integration is `SignPath/github-action-submit-signing-request` ([repo](https://github.com/SignPath/github-action-submit-signing-request)).
- **Self-signed.** `New-SelfSignedCertificate -Type CodeSigningCert` creates a certificate "for testing purposes" ([cmdlet reference](https://learn.microsoft.com/en-us/powershell/module/pki/new-selfsignedcertificate)); per Microsoft it yields the same SmartScreen result as no signature ([SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)).
- **Buying a certificate.** Since June 1, 2023 the CA/Browser Forum requires subscriber private keys for all code signing certificates to be generated and stored in a hardware crypto module, so OV/EV certificates bought from a CA arrive on a token or HSM ([CA/B Forum Code Signing Requirements](https://cabforum.org/working-groups/code-signing/requirements/)).

### Linux

- **Not required.** "Artifact signing is not required for your application to be deployed on Linux." AppImage supports optional GPG signing via `SIGN=1`, `SIGN_KEY`, `APPIMAGETOOL_SIGN_PASSPHRASE`, but "AppImage does not validate the signature" ([Linux signing](https://v2.tauri.app/distribute/sign/linux/)). RPM supports optional GPG signing via `TAURI_SIGNING_RPM_KEY` / `TAURI_SIGNING_RPM_KEY_PASSPHRASE` ([RPM](https://v2.tauri.app/distribute/rpm/)). The Debian guide documents no signing ([Debian](https://v2.tauri.app/distribute/debian/)). The `/distribute/sign/` overview URL returned 404 at access time.

## CI on GitHub Actions

- **Runners.** `ubuntu-latest` = Ubuntu 24.04 x64; `ubuntu-22.04`, `ubuntu-24.04-arm`, `ubuntu-22.04-arm` are GA; `windows-latest` = Windows Server 2025 (`windows-2022` still GA); `macos-latest` = macOS 26 arm64; Intel macOS is `macos-26-intel` / `macos-15-intel`; macOS 14 is deprecated and macOS 13 is gone ([runner-images README](https://github.com/actions/runner-images)). Standard runners are "free and unlimited on public repositories", including arm64 ([GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)); for private repos the listed rates are Linux $0.006/min, Windows $0.010/min, macOS $0.062/min ([Actions billing](https://docs.github.com/en/billing/managing-billing-for-github-actions/about-billing-for-github-actions)).
- **Preinstalled.** Windows 2025 and 2022 images: Rust 1.98.0, Node 22.23.2, WiX Toolset 3.14.1.8722, Visual Studio Enterprise 2022; NSIS 3.10 is listed only on the 2022 image ([Windows2025](https://github.com/actions/runner-images/blob/main/images/windows/Windows2025-Readme.md), [Windows2022](https://github.com/actions/runner-images/blob/main/images/windows/Windows2022-Readme.md)). Since the bundler downloads WiX/NSIS itself (see Bundles), neither preinstall is load-bearing. macOS 26 arm64: Rust 1.97.1, Node 24.18.0, Xcode CLT 26.6; macOS 15 arm64: Rust 1.97.1, Node 22.23.1, Xcode CLT 16.4 ([macos-26](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md), [macos-15](https://github.com/actions/runner-images/blob/main/images/macos/macos-15-arm64-Readme.md)). Ubuntu 22.04/24.04: Rust 1.98.0, Node 22.23.2; WebKitGTK dev packages are not preinstalled ([Ubuntu2204](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2204-Readme.md), [Ubuntu2404](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2404-Readme.md)).
- **Linux deps.** Tauri's prerequisites: `libwebkit2gtk-4.1-dev build-essential curl wget file libxdo-dev libssl-dev libayatana-appindicator3-dev librsvg2-dev` ([prerequisites](https://v2.tauri.app/start/prerequisites/)). The CI example uses the shorter `libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf xdg-utils` on `ubuntu-22.04` ([GitHub pipeline guide](https://v2.tauri.app/distribute/pipelines/github/)). The Ubuntu 22.04 choice follows the glibc baseline rule in the Linux bundle guides above.
- **Reference workflow.** Matrix: `macos-latest` twice (`--target aarch64-apple-darwin`, `--target x86_64-apple-darwin`, both targets installed via `dtolnay/rust-toolchain@stable` `targets:`), `ubuntu-22.04`, `windows-latest`, optionally `ubuntu-22.04-arm` for public repos; `actions/setup-node` LTS; `swatinem/rust-cache@v2` with `workspaces: './src-tauri -> target'`; frontend install step; `tauri-apps/tauri-action@v1` with `tagName: app-v__VERSION__`, `releaseName`, `releaseBody`, `releaseDraft: true`, `prerelease: false`, `args: ${{ matrix.args }}`, `env: GITHUB_TOKEN`; `permissions: contents: write` at job level. The guide notes the default `GITHUB_TOKEN` is read-only unless the repo's Actions setting grants "Read and write permissions" ([GitHub pipeline guide](https://v2.tauri.app/distribute/pipelines/github/)). Emulated ARM via `pguyot/arm-runner-action` is described as much slower (about an hour uncached).
- **tauri-action behavior.** Runs the project's Tauri CLI (`npm|pnpm|yarn|bun tauri` or `tauriScript`), installing `@tauri-apps/cli` globally if none is found; replaces `__VERSION__` in `tagName`/`releaseName`; creates the release for `tagName` or uploads to an existing `releaseId` ("If set, `tagName` and `releaseName` will NOT be considered to find a release"); with an existing draft, `releaseDraft` must be `true`; `projectPath` must not be gitignored; `uploadPlainBinary` is off because "Tauri doesn't officially support a portable mode"; `uploadWorkflowArtifacts` (default `false`) can also publish bundles as workflow artifacts; runs on `node24`. Outputs: `releaseId`, `releaseHtmlUrl`, `releaseUploadUrl`, `artifactPaths`, `appVersion` ([tauri-action README](https://github.com/tauri-apps/tauri-action), [action.yml](https://github.com/tauri-apps/tauri-action/blob/dev/action.yml)). The multi-job example `publish-to-manual-release.yml` creates a draft release with `actions/github-script`, passes `release_id` to a matrix of tauri-action jobs via `releaseId`, then a final job flips the draft to published ([example](https://github.com/tauri-apps/tauri-action/blob/dev/examples/publish-to-manual-release.yml)). Signing secrets are the env vars from the signing section (`TAURI_SIGNING_PRIVATE_KEY[_PASSWORD]`, `APPLE_*`, `WINDOWS_CERTIFICATE*` or Azure creds), not action inputs.
- **GitHub mechanics.** Secrets over 48 KB need the encrypted-file workaround; binary blobs are stored base64-encoded (`base64 -w 0` / `base64 -i ... -o ...`) and decoded in the job; secrets other than `GITHUB_TOKEN` are not passed to fork-triggered runs ([using secrets](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions)). "Events triggered by the `GITHUB_TOKEN` will not create a new workflow run" (except `workflow_dispatch`/`repository_dispatch`), so a release or tag created by a workflow with `GITHUB_TOKEN` does not re-trigger `on: push: tags` ([GITHUB_TOKEN concepts](https://docs.github.com/en/actions/concepts/security/github_token)). `softprops/action-gh-release` creates the release for the tag or, "If a tag already has a GitHub release, the existing release will be updated with the release assets"; current major is v3 ([action-gh-release](https://github.com/softprops/action-gh-release)).
- **Fit with the existing `release.yml`.** The current workflow triggers on any tag push (`tags: ["*"]`), grants `contents: write`, builds with `cargo build --release --locked` on `ubuntu-latest` / `windows-latest` / `macos-latest` (arm64 only, no Intel macOS), installs `libgtk-3-dev libxkbcommon-dev pkg-config` on Linux for the egui build, packages the bare executable into `.tar.gz`/`.zip` via `actions/upload-artifact@v7`, and a second job downloads the artifacts and publishes them with `softprops/action-gh-release@v3` ([`.github/workflows/release.yml`](../../.github/workflows/release.yml)). Against the facts above: (a) the trigger and permissions are compatible with tauri-action, but tauri-action itself creates or fills the release, so either the existing publish job goes away or the workflow adopts the create-draft / `releaseId` / undraft pattern; (b) `latest.json` and `.sig` uploads only come from tauri-action's release upload, not from `upload-artifact` + `action-gh-release`; (c) the Linux apt list must become the WebKitGTK 4.1 list, and `ubuntu-latest` (24.04) conflicts with the docs' Ubuntu 22.04 glibc baseline for AppImage/deb; (d) Intel macOS requires a second matrix entry (`--target x86_64-apple-darwin` on the arm64 runner, or a `-intel` runner), and `universal-apple-darwin` is the single-artifact alternative; (e) Node and a frontend install step are new; (f) bare-binary archives stop being the artifact (Tauri has no supported portable mode), replaced by the per-OS bundles.

## Nix

- **`cargo-tauri`.** In nixpkgs at `pkgs/by-name/ca/cargo-tauri/package.nix`, version 2.11.4 on nixpkgs-unstable `e8be7818` (built from tag `tauri-cli-v2.11.4`); `meta.platforms` includes `x86_64-linux`, `aarch64-linux`, `aarch64-darwin`, and it is not marked broken (`nix eval github:NixOS/nixpkgs/nixpkgs-unstable#cargo-tauri.version`; [package.nix](https://github.com/NixOS/nixpkgs/blob/master/pkgs/by-name/ca/cargo-tauri/package.nix)).
- **`cargo-tauri.hook`.** A setup hook (`passthru.hook`) that replaces `cargoBuildHook`/`cargoInstallHook`: it runs `cargo tauri build --bundles <type> --target <host-triple> [--debug] $tauriBuildFlags -- -j $NIX_BUILD_CORES --offline --profile ...`, where the default bundle type is `deb` on Linux and `app` on Darwin (`tauriBundleType` overrides); install copies `bundle/deb/*/data/usr/*` into `$out` on Linux and `bundle/macos/*.app` into `$out/Applications` on Darwin; on Linux it adds GStreamer plugin paths and `__NV_DISABLE_EXPLICIT_SYNC=1` to the gapps wrapper. `buildAndTestSubdir` (e.g. `src-tauri`) is supported by appending `build.target-dir` to `config.toml` because "Tauri doesn't respect `$CARGO_TARGET_DIR`" ([hook.nix](https://github.com/NixOS/nixpkgs/blob/master/pkgs/by-name/ca/cargo-tauri/hook.nix), [hook.sh](https://github.com/NixOS/nixpkgs/blob/master/pkgs/by-name/ca/cargo-tauri/hook.sh)). The hook's platforms are Linux and Darwin only; it produces deb/app, not AppImage, MSI, or DMG.
- **Reference derivations.** The nixpkgs manual's hook section shows `rustPlatform.buildRustPackage` with `npmDeps = fetchNpmDeps {...}`, `nativeBuildInputs = [ cargo-tauri.hook nodejs npmHooks.npmConfigHook pkg-config ] ++ (Linux: wrapGAppsHook4)`, `buildInputs = (Linux: glib-networking openssl webkitgtk_4_1)` ("Most Tauri apps need networking"), `cargoRoot = "src-tauri"`, `buildAndTestSubdir = cargoRoot`, and documents `tauriBuildFlags`, `tauriBundleType`, `dontTauriBuild`/`dontTauriInstall`/`dontTauriFixup` ([nixpkgs manual: cargo-tauri.hook](https://github.com/NixOS/nixpkgs/blob/master/doc/hooks/tauri.section.md)). nixpkgs' own hook test builds Tauri's example app with `pnpm_10` + `pnpmConfigHook` + `fetchPnpmDeps`, `rustPlatform.cargoSetupHook`, `wrapGAppsHook4`, `buildInputs = [ openssl ] ++ (Linux: glib-networking libayatana-appindicator webkitgtk_4_1)`, `buildAndTestSubdir = "examples/api/src-tauri"`, and patches `libappindicator-sys` to the nix store path of `libayatana-appindicator3.so.1` ([test-app.nix](https://github.com/NixOS/nixpkgs/blob/master/pkgs/by-name/ca/cargo-tauri/test-app.nix)).

## Cross-cutting notes

- Each OS has two independent signatures in play: the OS trust signature (Developer ID + notarization, Authenticode; none on Linux) and Tauri's minisign updater signature, which is mandatory for the updater on every OS and has no rotation path.
- The updater cannot update deb/rpm installs; on Linux only the AppImage is self-updating, and the AppImage guide's Ubuntu 22.04 baseline conflicts with `ubuntu-latest` (24.04).
- Both Apple (Sequoia) and Microsoft (SmartScreen, Smart App Control) put unsigned software behind an explicit user override; on Windows even a paid OV/EV certificate starts with a warning until reputation accrues, and Microsoft states EV no longer buys immediate reputation.
- Free signing paths for an OSS project: Linux (nothing needed), SignPath Foundation on Windows (with its policy/process obligations), none on macOS (USD 99/year program is the only route to notarization). Azure Artifact Signing is the paid CI-native Windows option and validates individuals only in the US/Canada.
- tauri-action covers building, release creation, asset upload, `.sig` upload, and `latest.json` generation in one step; the existing two-job `release.yml` shape maps onto its `releaseId` pattern rather than onto `action-gh-release`.
- Under Nix, `cargo-tauri.hook` yields a deb-derived `$out` (Linux) or `.app` (Darwin) for `nix build`; AppImage/MSI/DMG/NSIS bundles are outside the hook and remain a CI concern.
